# ESP32 Android Agent 整体设计

状态：设计基线，尚未代表已经实现或已经实机验证的功能。

参考项目：<https://github.com/onehumanbeing/esp32-iphone-agent>，参考提交 `27f36ce0f5d2d520ad5a45a0eea6eb99abbbe6f7`。

## 1. 项目定位和设计原则

让个人用户在自己的电脑上，通过视觉模型和 ESP32 操作真实安卓手机；同时让没有硬件的新用户能先体验，贡献者能在没有手机和板子的情况下开发核心模块。

- ESP32 HID 是项目的主要控制方式；ADB 控制是体验、开发和诊断入口。
- 默认使用 ADB 获取画面，不要求安装安卓伴侣 App，不要求 Root。
- 本地部署，无项目账号、项目云服务或指定模型供应商要求；支持 OpenAI 兼容视觉模型接口。
- 首版单手机、单任务、单控制者。先交付可安装、可诊断的完整链路，再扩展设备和功能。
- 保持 Python + FastAPI + 轻量静态网页，普通用户无需安装 Node.js、前端构建工具或 Docker。
- 优先复用参考项目和成熟依赖；仅抽象画面与控制边界，不建设通用插件平台。

## 2. 用户入口和连接方式

| 使用方式 | 画面 | 控制 | 用途 |
|---|---|---|---|
| ADB 体验模式 | ADB 截图，优先 USB 连接 | ADB 基础输入 | 无硬件体验、模型验证、开发与诊断 |
| ESP32 主模式 | 无线 ADB 截图 | ESP32-S3 USB HID | 正式硬件使用 |
| 经典 ESP32 主模式 | USB 或无线 ADB 截图 | 电脑 USB 串口 → ESP32 BLE HID | 常见 ESP32/WROOM，板子留在电脑，无需板子 Wi-Fi |
| 手动操作 | 与当前模式共用 | 与当前模式共用 | 无模型验证连接、校准和人工接管 |

ESP32 插入手机时，手机通常作为 USB 主机。普通连接方式下，不能假定同一 USB 口还能同时通过 USB ADB 连接电脑。ESP32 主模式因此以无线 ADB 为默认画面通道，USB 扩展坞不作为解决双角色问题的默认方案。

当前连接板由 esptool 实测为 ESP32-D0WD-V3 v3.1 / 4MB。经典 ESP32 无原生 USB HID，采用电脑串口控制 + BLE 键鼠连接手机；此时手机 USB 口可继续连接电脑运行 ADB。该路线不需要配置板子 Wi-Fi，先在手机系统蓝牙设置主动配对，再在网页绑定当前手机并校准。S3/S2 的原生 USB 路线保留，但不将芯片能力视为已构建或已实测固件。

Android 11 及以上优先使用系统无线调试配对。旧系统提供先通过 USB 开启 ADB TCP/IP、再接 ESP32 的兼容流程。连接向导区分配对端口和连接端口，优先自动发现，支持手动地址兜底。

无线调试、网络变化、设备重启可能需要用户恢复连接；向导报告实际状态，不承诺永久自动连接。不要自动切换控制后端；操作开始前明确展示当前控制方式。

## 3. 新用户流程

### 无硬件体验

1. 下载对应平台的发布包，运行启动器。
2. 连接手机，按向导开启 USB 调试并授权电脑；检查 ADB 状态。
3. 在网页确认画面，执行一次手动点按，验证坐标和输入通道。
4. 填入模型地址、模型名和密钥，测试连接；手动模式不要求模型配置。
5. 运行打开设置等示例任务，查看动作和验证结果。

### 使用 ESP32

1. 完成手机无线 ADB 配对并确认能获取画面。
2. 将 ESP32 接到电脑，通过向导选择受支持板型、刷入发布固件并写入 Wi-Fi、服务端地址和配对信息。
3. 把 ESP32 插入支持 USB OTG 的手机。服务端确认板子身份，并让用户确认该板子对应当前手机。
4. 完成鼠标校准和手动操作检查，进入硬件模式。

固件配置保存在设备 NVS；调整配置不要求修改源码或重新编译。模型配置与连接信息保存在本机用户配置目录，不要求用户手动编辑 `.env`。源码用户仍可通过环境变量配置。

经典 ESP32 串口 BLE 路线无需上述 Wi-Fi 配置：板子保持插在电脑上，手机蓝牙配对，网页显式切换BLE控制，鼠标校准保存在本机并绑定手机和完整截图尺寸。当前未验证的Android特殊导航键不进入BLE能力集。详见 [BLE使用说明](BLE-SETUP.md)。

## 4. 软件架构

```text
浏览器控制台
      │ 本地 HTTP / 事件推送
      ▼
Python 服务端
  ├─ 连接向导与设备会话
  ├─ ScreenSource ── ADB 截图
  ├─ Controller ──── ESP32 HID / ADB 控制
  ├─ TaskRunner ──── 规划 → 观察 → 执行 → 验证
  ├─ ModelClient ─── OpenAI 兼容视觉模型
  └─ TraceStore ──── 动作、结果、耗时、可选截图
```

### 小而明确的接口

- `ScreenSource`：返回图像、帧编号、接收时间、尺寸、方向和连接状态。
- `Controller`：返回支持的动作能力，执行规范动作，停止当前操作并释放输入。
- `DeviceSession`：绑定当前手机、画面来源、控制器和校准信息，保证它们属于同一使用会话。
- `TaskRunner`：维护任务状态、模型调用和结果验证，不依赖具体的 ADB 或固件实现。

ADB 操作复用同一个受管理的子进程调用层，使用参数列表调用，限制超时并解析设备状态。禁止通过任意 shell 字符串拼接执行模型输出。

服务启动后通过应用生命周期初始化模块，避免在模块导入时创建设备连接、模型客户端或启动投屏进程。

## 5. 画面与坐标

首版按需通过 `adb exec-out screencap -p` 获取截图，验证图像完整性并限制并发。动作前获取新截图，动作后轮询等待结果；网页预览使用较低频率的最新帧，不积压截图请求。

scrcpy 是可选的流畅桌面预览工具。它默认提供桌面窗口，不直接提供网页视频或 JPEG API。高帧率网页预览作为后续工作，实施时固定并验证视频桥接方式和 scrcpy 版本；不要把桌面窗口截图当作默认采集链路。

- 模型使用 0–1000 的统一坐标，由服务端转换至完整手机截图坐标。
- 网页计算图像实际显示区域，剔除留白；模型缩放、裁剪、旋转均保留变换信息。
- 横竖屏、分辨率变化后作废旧截图与不适用的校准，重新观察。
- 每帧记录服务端单调时钟接收时间；跨设备时钟不直接比较。
- 模型返回后检查画面年龄和目标区域变化；已经失效的动作重新决策。
- 界面稳定通过实际图像变化判断，不能以持续视频流是否停止到帧作为依据。
- 黑屏、锁屏、受保护画面和截图失败作为独立状态处理，画面不可用时停止自动操作。

## 6. Agent 执行闭环

状态流程：`idle → planning → observing → executing → verifying`；可以进入 `paused`、`completed`、`failed` 或 `stopped`。断线进入暂停或失败，恢复后重新观察；不自动重放结果未知的动作。

模型输出规范动作、简短动作说明和预期可观察结果。兼容支持结构化输出的模型和严格解析的普通兼容接口。服务端验证动作类型、参数范围、文本长度和持续时间，再交给控制器。

初始动作：点按、带时长滑动、长按、滚动、ASCII 输入、受支持按键、主页、返回、最近任务、等待、结束。能力由控制器和设备配置报告；不支持的动作不进入模型的可选集合。

首版每次执行一个改变界面的动作，随后重新取图验证。主页、返回等 HID 映射经过实机验证后加入设备配置；不假定键盘 Home 键等同于安卓主页。

验证区分三个层次：命令收到、输入输出完成、手机状态符合预期。像素差异仅作为辅助信号，不能单独证明任务成功。预期结果由当前画面和必要的模型判断验证；最终结束也要检查目标是否达到。

连续失败优先识别定位错误、加载未完成、画面失效和规划错误。分别执行有限重定位、等待、刷新观察或重新规划，并设置步数、时间及费用上限。

规划模型仅在任务开始、必要阶段切换或卡住时调用；执行模型优先速度。模型输出只请求用户可理解的动作说明，不要求输出完整思维过程。

## 7. 固件与控制可靠性

首版使用相对鼠标和键盘，支持按设备、屏幕方向保存校准；绝对坐标与触摸 HID 需要单独的机型兼容验证后再提供。

固件协议增加版本、设备身份、会话编号、命令编号、边界校验和明确结果。握手交换能力，协议版本不匹配时给出升级提示。输入命令有长度和时长上限，不允许换行文本变成额外命令。

移动、拖动和长按通过短周期动作调度执行，期间处理停止与连接状态。取消后清空待执行动作，释放鼠标与键盘。Wi-Fi、服务端连接或心跳失效时释放输入，重连后建立新会话。

点击和输入发生超时时可能已经生效，不能按普通幂等请求自动重试。先验证手机状态；同一会话的重复命令编号可以去重，但断线前的未知结果仍需观察。

人工操作与 Agent 共用一个动作调度器。接管先暂停任务、取消待执行动作并释放输入，再允许手动控制；恢复后重新观察和规划。

## 8. 中文输入和其他可选能力

普通 HID 键盘和基础 ADB 文本输入都不能保证任意 Unicode 输入。首版明确标注 ASCII 能力；Unicode 作为可选输入法扩展，优先评估成熟开源实现，用户需要主动安装、启用和选择输入法。

Unicode 输入使用当前获得焦点的输入连接，执行后检查结果。未启用、无焦点或超时需要明确反馈，不盲目重复输入。

安卓伴侣 App 保留为后续可选画面来源，用于不希望使用 ADB 的用户。它引入安装、MediaProjection 授权、前台服务和后台生命周期适配，不进入首版默认依赖。

其他后续能力：scrcpy 视频接入、绝对坐标 HID、局部 OCR、任务模板、多设备管理、外部 API/MCP 集成。根据实际成功率和用户需求逐项增加。

## 9. 网页、配置和记录

沿用参考项目的轻量网页，优先完善连接向导、画面、手动控制、模型设置、任务过程和紧急停止。状态更新可以通过 SSE 实现，避免每次轮询传输完整历史。首版不引入独立前端工具链。

模型密钥保存在本机配置中，界面显示掩码，日志和错误信息脱敏。记录保存动作、验证结果、耗时和错误；截图保存可配置，并提供清理与导出。

网页默认仅监听本机；板子连接端口独立对局域网开放并校验设备配对信息。远程网页访问属于显式配置，启用后要求会话鉴权。截图和任务数据只进入本机记录及用户配置的模型服务。

## 11. 发布、贡献与验证

- 首个完整用户发布包优先 Windows，同时保留 macOS/Linux 源码安装入口；对应平台验证通过后再发布便携包。
- 发布包提供启动器、必要运行时、静态资源、已验证固件和依赖清单。可再分发依赖随包提供；其他依赖由启动器按明确来源安装。用户无需安装 Arduino 开发环境。
- 首版固件支持一个明确板型与构建配置，记录引脚、USB、Flash 配置；增加板型需要构建和实机证据。
- CI 运行 Python 静态检查、关键单元测试、协议与模拟设备集成测试，以及固件编译。
- 贡献者可以用假屏幕、假控制器和假模型验证完整任务状态流，无需真实手机或付费模型。
- 真实手机验收单独执行并记录机型、Android 版本、板型、连接方式和模型配置；软件测试与固件编译不等同于硬件验证。
- 核心验收覆盖：坐标与旋转、长按和滑动、取消、断线、未知动作结果、人工接管及任务目标验证。
- 性能报告给出成功率、动作延迟、任务时间、重试次数和模型费用，并注明条件；不预先承诺通用机型的帧率与成功率。

## 12. 实施顺序与首版完成条件

1. 建立可独立运行的服务端，移植网页和模型接口，接入 USB ADB 截图与手动控制，完成连接诊断。
2. 接入结构化动作、任务状态、结果验证和记录，完成 ADB 体验模式及模拟集成测试。
3. 移植并改进 ESP32 固件、运行时配置和可中断执行，接入无线 ADB、校准及 ESP32 主模式。
4. 完成 Windows 启动器、预编译固件、快速开始、依赖清单和至少一套实际手机/板子的验收记录后，发布 v0.1。
5. 根据反馈增加 Unicode 输入扩展、视频预览性能和更多已验证板型/机型；伴侣 App、多设备和绝对坐标 HID 后续评估。

v0.1 包含 ADB 体验路径和可使用的 ESP32 主路径。画面丢失时停止自动操作；停止和断线能够释放输入；用户通过向导完成配置，不需要改代码。实际成功率与延迟以验收记录为准。
