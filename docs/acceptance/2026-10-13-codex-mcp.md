# Codex MCP 验收（2026-10-13）

OpenSpec：`add-mcp-device-tools`。新增工具不修改固件；当前验收仅覆盖所列环境。

## 环境与方法

- Windows主机，Python3.12.14及3.10.21，官方Python MCP SDK1.30.0。
- 实际Codex CLI0.154.0，通过stdio注册`android_agent`，桥接已运行的本机工作台。
- CLI使用`codex exec --ephemeral --json -s read-only`和单次`-c mcp_servers=…`覆盖，未修改用户全局配置。仅对已授权测试设置`tools.android_action.approval_mode="approve"`，其他审批设置保持；提示限定仅调用四个MCP工具，不用shell/其他工具控制手机。
- 模拟服务：`python server/tests/mcp_demo.py --port 8900`，图像明确标记DEMO/NO REAL HARDWARE。
- 实机：Redmi Note14 5G（24094RAD4C），Android15/API35，完整截图1080×2400；ESP32-D0WD-V3 rev3.1/4MB/esp32dev/COM5，BLE0.1.4；沿用已验证531/1176计数校准。ADB仅作为画面源，输入模式为BLE。
- 手机Edge打开`python server/tests/mcp_demo.py --phone-page --port 8901`提供的本机页面，ADB reverse仅用于页面准备；测试页不提交至外部服务。验收输入由Codex经MCP发出，服务内存事件和后续截图独立核验。

原始CLI JSONL包含图片，仅保存在被忽略的`.runtime-local/mcp-*.private.jsonl`，不提交设备配置、模型凭据或私人画面。stdio SDK测试不能代替这里的实际Codex调用。

## 发现与修复

首次实际Codex调用时，返回结果同时包含ImageContent与structuredContent。SDK和CLI协议日志都能收到JPEG，但Agent只读取了结构化元数据，主动停止而未发输入。截图成功结果改为TextContent元数据+ImageContent、不重复填structuredContent后，Codex能辨认实际图像。

第二次验收确认可见图像，但`approval_policy=never`与默认工具审批策略拒绝了动作，没有输入送达。之后只为用户已授权的本次测试动作设置明确预批准，不改变工具副作用标记或全局策略。不是通过改变工具为只读来绕过审批。

## 实际Codex模拟验收

通过：状态→截图→tap→截图→旧凭据重复tap（拒绝）→新截图→type→截图→stop。

- Codex从真实返回图像识别“MCP TAP TEST”，选择归一化`(500,301)`；新截图显示“MCP TAP OK”。
- 使用第一次observation_id重复tap一次被拒绝，无重试。
- DEMO无真实编辑焦点，Codex直接发`type: mcp_hello`；新截图显示“Input: mcp_hello”。这是模拟输入，不能证明手机IME或HID键盘。
- stop返回`ok=true / cancelled=true / release=no_held_input`。
- 后续完善稳定错误码，旧凭据错误明确为`stale_observation`；测试覆盖该实际code。

## 实际Codex手机验收

首轮部分通过，保留失败：

- Codex看图选择`(500,368)`，后续实际截图显示“MCP TAP OK — 1”。手机本机事件记录一个tap和对应pointerdown/up。
- 用旧observation_id重复tap一次返回`stale_observation`；后续截图和事件均确认计数仍为1，没有再次点击。
- Codex把输入框定位为`(500,714)`，实际落在框下方。随后type命令`mcp_hello`返回完成，但后续截图/输入事件显示仍为空，未建立焦点。它停止并明确报告部分通过，没有盲目重放。这是模型定位失误，不能将命令完成记为文字验收通过。
- stop返回`hid_release_sent`。首次页面共两个pointerdown和两个pointerup，无输入事件。

随后在独立端口8903运行带FOCUS OK视觉提示的同一本机测试页，第二轮通过：

- 已知首轮定位错误后，提示要求重新观察、计算输入框中心（准备页面约500/670）并先验证焦点。Codex实际看图选择`(500,670)`，只点击一次，新截图确认“FOCUS OK - ASCII input active”。
- 新观察后只提交一次`type: mcp_hello`，手机页面记录9次逐字符input事件，最后值精确为`mcp_hello`。
- Codex再次通过MCP获取图像，输入框和“Input: mcp_hello”同时显示准确英文；屏幕键盘展开使布局移动，重新截图仍保持完整画面映射。
- 最后调用android_stop返回`ok=true / cancelled=true / release=hid_release_sent`，无固件操作。此轮1次pointerdown与1次pointerup配对，没有Enter或提交。

结论：实际Codex已通过MCP看见并核验真实手机BLE点击、ASCII输入、重复凭据拒绝及停止报告。**首轮模型自行定位输入框失败，第二轮在中心位置提示与焦点确认帮助下成功**；这不是任意模型/页面一次成功率或全屏像素精度证明。

首轮失败证据保留。重启旧8901测试服务的停止命令被自动审批审查拒绝，返回“blocked by policy”，没有更详细理由；未重试停止，旧服务保持运行。
